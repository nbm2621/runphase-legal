Runphase is an Atlassian Forge app for running planned changes against a Jira issue: authoring a procedure, executing it step by step, and leaving an immutable record of what happened.

This policy describes what the app accesses, what it stores, and where that data lives. It is short because the app is deliberately narrow.

Nothing leaves Atlassian

Runphase has no egress. Its manifest declares no remotes and no external permissions, so the app cannot make a network request to anywhere outside Atlassian, and it does not.

There is no analytics, no telemetry, no error reporting service, no advertising and no third-party processor of any kind. Every deployment is reported by Atlassian as eligible for Runs on Atlassian, which means the app's code and data stay within Atlassian's infrastructure and data residency guarantees.

The vendor cannot read your data. Runphase stores everything in Forge app storage, which is scoped to your installation; there is no vendor-side database, dashboard or export.

What the app accesses

Runphase requests three permission scopes and no others:

ScopeWhat it is used for
read:jira-work Reading the Jira issue a run belongs to — its key, id, project key, summary and status — to identify the change and snapshot how it looked when the window opened.
read:jira-user Resolving Atlassian account ids to display names, so a run's history reads as names rather than ids.
storage:app The app's own storage, described below.

All three are read-only with respect to Jira. Runphase never writes to Jira — it does not create, edit, transition or comment on issues, and it does not push execution content back into Jira automatically.

Permission checks are made as the signed-in user, so Runphase shows a person only the runs whose underlying Jira issue they could already open. If Jira refuses or cannot answer, the app fails closed and says so.

What the app stores

In Forge app storage, scoped to your installation:

  • Run records — the Jira issue key and id, project key, the issue summary snapshotted as the run's title, the run's state, planned and actual windows, and timestamps.
  • Atlassian account ids for the people who created, started and closed a run, and who wrote each note or deviation. Account ids, not names.
  • Text you enter — plan steps and their expected results, success criteria, rollback procedures, step notes, deviations, evidence references, and reasons given for failing or rolling back a run.
  • An event log of what happened during the run, which is append-only.
  • Templates saved from a run's plan, so a procedure can be reused. A template records the Jira issue it was saved from, and is offered only to people who could open that issue.
  • A per-viewer cache of display names — a map of Atlassian account id to display name, at most 200 entries, each name kept for six hours and each "no name available" for fifteen minutes. It exists to avoid re-asking Jira on every page load, and is keyed to the viewer because the lookup runs with that viewer's permissions.

Sensitive content, and what you can do about it

Runphase is an execution-record system, not a secrets repository.

The app screens text for patterns that look like credentials before storing it and blocks the write with a warning naming the field. Because engineers legitimately paste command output, that block can be overridden deliberately — the override is a recorded act with an author, not a silent default.

The screen is a heuristic. It will not catch everything.

Redaction. Anything recorded can be redacted afterwards, including on a closed run. A redaction overwrites the value everywhere the app holds it — the live record, the frozen copy in the run record, and the event log — and leaves a marker saying who redacted it and when, but never what it was.

Redaction is not containment, and the app says so where it offers it. A credential that was recorded may already exist in an export someone took, a Jira comment, a chat message or a screenshot, none of which Runphase can reach. If a live credential is recorded, rotate it. Redaction removes it from this app; only rotation makes it harmless.

Retention and deletion

A run record is immutable once the run reaches a terminal state, and notes are append-only. That is the product's purpose: a record that can be edited after the fact is not a record. Redaction, described above, is the single exception.

Runphase does not delete data on a schedule and has no retention timer.

Uninstalling the app removes its storage according to Atlassian's standard Forge app data deletion process. If you need data removed before then, contact the address at the top of this policy.

Cookies and tracking

Runphase sets no cookies and uses no tracking technology. Its interfaces run inside Atlassian-provided iframes and store nothing in your browser beyond what Atlassian itself sets.

Changes to this policy

Material changes will be reflected here with a new effective date. Because the app's scopes and egress posture are declared in its manifest and enforced by Atlassian, a change in what the app can access is not something that can happen quietly — it requires a new version and, for a new scope, your re-consent at install time.
